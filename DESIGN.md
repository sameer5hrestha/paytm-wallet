# Wallet transfer — design and reasoning

**Data model.** A user has one wallet enforced by a unique `user_id`. Balances and transfer amounts use integer `BIGINT` paise, with database checks against negative balances and nonpositive transfers. Transfers persist the originating user, sender, recipient, amount, stable terminal outcome, and a unique `(user_id, idempotency_key)`. A protected demo-only provisioning endpoint assigns an initial endowment once; test conservation is measured after wallet creation.

**Simplest correct mechanism.** Each transfer runs in one PostgreSQL READ COMMITTED transaction. After claiming the idempotency key, it locks both wallet rows in ascending database UUID order using `FOR NO KEY UPDATE`, checks funds and recipient overflow, performs debit/credit, and records COMPLETED or DECLINED. This lock excludes competing balance writers but is compatible with foreign-key KEY SHARE locks; stronger FOR UPDATE can cause lock-upgrade deadlocks after transfer insertion. Every transfer uses the same lock order, including A→B versus B→A. Concurrent get-or-create uses `INSERT … ON CONFLICT DO NOTHING` and a fresh SELECT.

**Idempotency and failure.** The unique key and both balance updates commit together. Concurrent duplicates wait at the uniqueness constraint; a new READ COMMITTED statement then sees and returns the committed winner. Different payloads conflict with 409. Declines are durable and replay unchanged even after funding. A rollback removes the provisional key and both movements. A crash after commit but before response is resolved with the same key. Bounded lock/statement timeouts surface 503; clients must retry the same operation, not invent another key.

**Alternatives rejected.** An in-memory lock/cache cannot coordinate multiple instances or survive restarts. Check-then-write races. SERIALIZABLE can be correct but needs serialization retry handling without simplifying this two-row operation. Conditional debit is also valid but, followed by credit, still locks two wallets and needs deadlock handling/order. Distributed locks, Kafka, sagas, and a separate idempotency store add failure boundaries with no benefit for one PostgreSQL transaction.

**Consistency versus availability.** Transfers require an authoritative database transaction; unavailable storage causes a retryable failure instead of accepting an unverified debit. This is a single-region demonstration, not a multi-region availability or failover guarantee. PostgreSQL durability settings are not weakened. Managed-host backup/HA guarantees must be checked separately.

**Operate and verify.** A multi-stage image runs as non-root with health checking. Compose starts app and PostgreSQL. The burst harness asserts wallet uniqueness, replay identity, exact balances, conservation and no overdrafts. JSON logs carry request correlation IDs and only describe committed money movements. Prometheus exposes HTTP latency/rate/errors and domain counters. Logs and counters can be lost in the post-commit crash window; the database result is authoritative. No production financial-audit guarantee is claimed.
